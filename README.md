# DiskBackuper

Минимальный технический прототип на C++ для Visual Studio 2022. На текущем
этапе он читает обычный файл блоками и записывает его в сегментированный образ
EnCase 6 (`E01`) через `libewf-legacy`.

## Подготовка зависимости

Откройте PowerShell в корне репозитория и выполните:

```powershell
.\scripts\bootstrap-libewf.ps1
```

Скрипт загружает официальный `libyal/libewf-legacy`, фиксирует проверенный
коммит, генерирует решение Visual Studio 2022 и собирает `Release|x64` с
поддержкой записи. Если Python не находится через `PATH`, передайте каталог с
`python.exe` параметром `-PythonPath`.

После этого откройте `DiskBackuper.sln`, выберите `Debug | x64` и соберите
решение.

## Проверка Phase 0

Создать тестовый файл размером 512 МиБ:

```powershell
.\x64\Debug\DiskBackuper.Phase0.exe --create-test-file `
    .\test-data\phase0-source-512MiB.bin 512
```

Создать E01 с сегментами по 32 МиБ:

```powershell
New-Item -ItemType Directory .\test-output -Force
.\x64\Debug\DiskBackuper.Phase0.exe --create-e01 `
    .\test-data\phase0-source-512MiB.bin `
    .\test-output\phase0-image 32
```

Команда не перезаписывает существующий первый сегмент `.E01`. Для повторного
запуска укажите другое базовое имя или предварительно переместите созданные
сегменты.

## Проверка файловой системы и восстановления

Создать 512-МиБ образ диска с MBR, разделом FAT32 и контрольными файлами:

```powershell
.\x64\Debug\DiskBackuper.Phase0.exe --create-fs-test-image `
    .\test-data\phase0-fat32-512MiB.img 512
```

Упаковать его в E01:

```powershell
.\x64\Debug\DiskBackuper.Phase0.exe --create-e01 `
    .\test-data\phase0-fat32-512MiB.img `
    .\test-output\phase0-fat32 32
```

Проверить E01 штатной утилитой `libewf`:

```powershell
.\.deps\libewf-legacy\vs2022\Release\x64\ewfverify.exe `
    .\test-output\phase0-fat32.E01
```

После открытия `phase0-fat32.E01` в R-Studio должен появиться раздел FAT32 с
меткой `DISKBACKUP` и следующими объектами:

- `README.TXT`;
- `MARKER1.TXT`;
- `RANDOM.BIN` размером 1 МиБ;
- `ZEROS.BIN` размером 2 МиБ;
- `DOCS\RECOVER.TXT`.

## Остановка и продолжение записи

Во время `--create-e01` можно нажать `Ctrl+C`. Программа закончит текущий
безопасный блок, зафиксирует незавершённый E01 и выведет позицию остановки.
Продолжить запись можно командой:

```powershell
.\x64\Debug\DiskBackuper.Phase0.exe --resume-e01 `
    .\test-data\phase0-source-512MiB.bin `
    .\test-output\phase0-resume
```

Для воспроизводимого теста без ручного нажатия `Ctrl+C` последний аргумент
`--create-e01` задаёт абсолютную позицию остановки в МиБ. Например, остановка
после 160 МиБ:

```powershell
.\x64\Debug\DiskBackuper.Phase0.exe --create-e01 `
    .\test-data\phase0-source-512MiB.bin `
    .\test-output\phase0-resume 32 160
```

При resume `libewf` сама определяет последнюю безопасную позицию. Она может
быть меньше позиции, показанной при остановке: незавершённый хвост отбрасывается
и записывается повторно. Исходный файл при продолжении должен быть тем же самым.

## Создание E01 с физического USB-накопителя

Команды физического чтения нужно запускать в PowerShell от имени
администратора. Сначала определите номер диска и его точный физический размер:

```powershell
Get-Partition -DriveLetter E | Get-Disk |
    Select-Object Number, FriendlyName, BusType, Size, IsBoot, IsSystem
```

Не копируйте номер и размер из примера вслепую. Прототип принимает только путь
вида `\\.\PhysicalDriveN`, открывает устройство с `GENERIC_READ` и отказывается
работать, если диск системный, не является съёмным USB-устройством или его размер
не совпадает с ожидаемым.

Проверить доступ и прочитать первый и последний сектор:

```powershell
.\x64\Debug\DiskBackuper.Phase0.exe --probe-device `
    \\.\PhysicalDrive2 4013948928
```

Создать сегментированный E01 (последний аргумент — предельный размер сегмента в
МиБ):

```powershell
.\x64\Debug\DiskBackuper.Phase0.exe --create-device-e01 `
    \\.\PhysicalDrive2 4013948928 `
    .\test-output\usb-e-4gb 512
```

Если запись была безопасно остановлена, продолжить её можно так:

```powershell
.\x64\Debug\DiskBackuper.Phase0.exe --resume-device-e01 `
    \\.\PhysicalDrive2 4013948928 `
    .\test-output\usb-e-4gb
```

Проверить контейнер и независимо посчитать MD5 всего физического устройства:

```powershell
.\.deps\libewf-legacy\vs2022\Release\x64\ewfverify.exe `
    .\test-output\usb-e-4gb.E01

.\x64\Debug\DiskBackuper.Phase0.exe --hash-device `
    \\.\PhysicalDrive2 4013948928
```

Для успешной побитовой проверки MD5, рассчитанный `ewfverify` из E01, должен
совпасть с `Device MD5`. Во время создания и контрольного хеширования не
изменяйте файлы на исходной флешке.

Если USB-источник внезапно отключён во время чтения, прототип отдельно
распознаёт ошибку источника. Обычный `--create-device-e01` сохраняет checkpoint
для последующего `--resume-device-e01`, но такой незавершённый контейнер нельзя
считать пригодным для открытия без исходного устройства.

Если приоритетом является восстановление уже скопированных данных без
повторного подключения источника, используйте потоковый режим:

```powershell
.\x64\Debug\DiskBackuper.Phase0.exe --create-survivable-device-e01 `
    \\.\PhysicalDrive2 4013948928 `
    .\test-output\usb-survivable 32
```

При потере USB этот режим создаёт корректный усечённый E01, размер носителя в
котором равен фактически скопированному безопасному префиксу. Такой образ можно
открывать без исходной флешки, но продолжить его до полного размера нельзя.
Ошибка записи выходного файла не считается потерей источника и не маскируется
этим механизмом.

Первый практический тест выполнен на FAT-флешке размером `4013948928` байт:
создание E01 завершилось без ошибок чтения, `ewfverify` вернул `SUCCESS`, а оба
MD5 совпали: `df0a7c6bbb02e1dc3c5b4bf4c70267bf`.

Практический тест аварийного отключения того же USB-накопителя также выполнен:

- флешка физически отключена после записи 640 МиБ;
- ошибка потери устройства распознана отдельно от ошибки назначения;
- частичный E01 финализирован, а безопасная позиция resume составила
  `549093376` байт (незавершённый хвост был автоматически отброшен);
- после подключения накопителя запись продолжилась до 100%;
- итоговый `ewfverify` вернул `SUCCESS`;
- MD5 завершённого E01 и текущего физического устройства совпали:
  `703aa2a675396fc5e1ecd8476513c89b`.

Отдельный тест окончательной потери источника выявил, что незавершённый
checkpoint с заявленным полным размером R-Studio не открывает. Этот результат
признан неприемлемым; для него добавлен описанный выше потоковый режим. Локальный
тест усечённого образа размером 250 МиБ прошёл `ewfverify: SUCCESS`; проверка
совместимости с R-Studio и повторный физический тест выполняются отдельно.

MD5 отличается от первого практического теста, то есть содержимое подключённой
FAT-флешки изменилось между испытаниями. Для следующей фазы одного совпадения
размера недостаточно: checkpoint должен хранить устойчивый идентификатор
устройства и fingerprint исходных секторов, а resume обязан проверить их до
дозаписи. Для криминалистически неизменяемого источника также нужен аппаратный
или программный write blocker.
